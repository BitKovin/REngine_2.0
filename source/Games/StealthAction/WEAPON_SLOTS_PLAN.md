# Weapon grid, akimbo and new HUD: implementation plan

This plan is for the implementer. It says what to build, in what order, and how to check each step. Visual reference: the HUD mockup artifact (`StealthAction HUD`, https://claude.ai/artifact/JV7xWuP8XpUJpXD4v5KnAA). All of its sizes are in UI units, which are the same units the engine uses (the UI is 1080 units tall).

When this plan and the code disagree, read the code again and then **stop and ask the owner**. Do not invent behaviour. A step marked **STOP** means: report what you found and wait.

## 0. Rules

1. Work only in `source/Games/StealthAction/`. Engine changes are allowed **only** where this plan lists them (§9). If you think you need another one, **STOP**.
2. Use the engine as it is: `Entity`, `IDrawMesh`, `StaticMesh`/`SkeletalMesh`, `RenderTexture`, `Framebuffer`, `ViewIdManager`, `Screenshot::RequestTarget`, `FileSystemEngine`, `CSVParser`, the markup UI (`UiElem`, `UiElem::Load`, `SetVar`, `SetClass`, `Find<>`). Read `Docs/UI/UI_Reference.html` sections 3, 5, 6, 8 and 10 before writing UI code. Do not write wrapper layers on top of them.
3. Search before you write a helper (`MathHelper`, `StringHelper`, `JsonHelper`, `CSVParser`). Never duplicate one.
4. Read files with `FileSystemEngine` (as `ItemsDataBase.cpp` does). Only the icon writer in §5 writes files.
5. Weapon switching in **Inventory mode** (`WeaponSystemMode::Inventory`, `InventoryMenu`) is out of scope. Do not change its behaviour. The new grid replaces only the **Slots mode** path.
6. Offhand weapons (cane, crucifix: `WeaponSlotData::offhand == true`) do not go into the grid. Their cycling (`offhandWeapons`, `desiredOffhandWeapon`) stays as it is.
7. Keep save compatibility: old saves must load. Every new serialized field has a default and is read with `DESERIALIZE_FIELD`-style "if present" logic.
8. Don't build or run the game unless the owner asks. The owner builds and checks in game. After each task, list exactly what the owner should look at.

## 1. Words used in this plan

| Word | Meaning |
|---|---|
| Column | One slot key, 1 to 6. Column index = `WeaponSlotData::slot` (0 to 5). |
| Entry | One cell of the grid: an owned weapon in **single** or **pair** (akimbo) form. |
| Pair | The akimbo form of an entry: two copies of the weapon, one in each hand. |
| Owned weapon | An item in `Player::ownedWeapons` with `offhand == false`. |
| Empty | A firearm whose magazine (both magazines for a pair) is 0 **and** whose ammo pool (`Player::GetAmmo(type)`) is 0. Melee weapons are never empty. |

## 2. Decisions already taken

These come from the owner's request. Don't change them without asking.

| # | Decision |
|---|---|
| D1 | The grid looks like the Max Payne switcher: one column per slot key, numbers on top, owned weapons stacked under the number. |
| D2 | Weapons the player doesn't own are **not drawn**. A column with nothing owned shows only its number. |
| D3 | An empty weapon is drawn darker. It stays in the grid. |
| D4 | A pair is drawn directly **under** its single version, in the same column. |
| D5 | Each weapon has an akimbo mode: `None`, `WithPerk` (pair appears only if the character has `AkimboPerk`), `Always` (pair appears for every character), `Only` (only the pair exists; no single entry). |
| D6 | One owned weapon is enough to get its pair. The player doesn't need to own two copies. |
| D7 | Icons are generated by rendering the weapon model into a render target, the same way the renderer draws meshes, on game start in builds without `DISTRIBUTION`. They are written into the game's **source** `GameData` so they get committed. Distribution builds only read them. |
| D8 | The HUD is rebuilt with the markup UI. Look: Max Payne layout (grid top centre, body figure + hourglass bottom left, ammo + weapon name bottom right), gothic: aged bone colour, dried blood, tarnished gold, blackletter names. No boxes, no panels, no rounded corners. |
| D9 | The temporary Akimbo power-up (`PowerUpManager::PowerUpType::Akimbo`) keeps working: while it is active, the current single firearm fires as a pair, exactly as today. |

Decisions this plan proposes. The owner may overrule them; they are marked so they're easy to change:

| # | Proposed decision |
|---|---|
| P1 | A number key on a column that holds the current entry steps **down** that column and wraps. On another column it selects that column's first entry. Mouse wheel / `weaponNext`/`weaponPrev` step through all entries in grid order (column by column, top to bottom). |
| P2 | Key and wheel selection **skip empty** entries. If every entry of a column is empty, the key does nothing. (Old-game behaviour. Ask the owner if he wants empty weapons selectable.) |
| P3 | A pair has a second magazine (`magazineAmmoLeft`). Shots alternate hands; a hand with an empty magazine is skipped. Reload fills the right magazine first, then the left. HUD shows `left · right / reserve`. |
| P4 | The grid shows for 2.2 s after any switch or key press, then fades out over 0.35 s. |

```cpp
enum class AkimboMode : uint8_t { None, WithPerk, Always, Only };

struct WeaponDef
{
    std::string className;
    int slot = 0;            // column 0..5
    int slotOrder = 0;       // row order inside the column, smaller = higher

{
public:

};
```

- `Player::AddWeapon` must use `WeaponDefs::Find(className)->slot` when the def exists, and fall back to `weaponData.slot` when it doesn't. (Pickups go through `AddWeaponByName` → `GetDefaultData()`, so the table wins over the C++ value.)

## 4. Weapon grid logic (Player)

### Task 4.1: the grid model

Add to `Player.hpp` (public):

```cpp
struct WeaponGridEntry
{
    std::string uuid;      // WeaponSlotData::inventoryUUID of the owned weapon
    std::string className;
    bool pair = false;
    int column = 0;
    int row = 0;           // filled by RebuildWeaponGrid, 0 = top
};

std::vector<WeaponGridEntry> weaponGrid;   // sorted: column, then slotOrder, then single before pair
WeaponGridEntry currentEntry;              // what the player holds / is switching to (uuid empty = nothing)
WeaponGridEntry lastEntry;                 // for the lastSlot key
int weaponGridRevision = 0;                // ++ every time weaponGrid or currentEntry changes; the HUD watches it

void RebuildWeaponGrid();
bool IsEntryEmpty(const WeaponGridEntry& entry);
void SelectGridEntry(const WeaponGridEntry& entry, bool forceChange = false);
void PressSlotKey(int column);
void StepWeapon(int direction);           // +1 / -1
```

`RebuildWeaponGrid()`:

1. Clear `weaponGrid`.
2. For each owned weapon in `ownedWeapons` with `offhand == false`, look up its `WeaponDef`. No def → use `Data.slot`, `slotOrder = 100`, `AkimboMode::None`.
3. Add the single entry unless the mode is `Only`.
4. Add the pair entry if the mode is `Always` or `Only`, or `WithPerk` and `AkimboPerk` is true.
5. If two owned weapons have the same `className`, add only the first one (the player sees one icon per weapon type). Keep this rule in one place with a comment.
6. Sort, assign `row` per column, `weaponGridRevision++`.
7. If `currentEntry` is no longer in the grid (the perk was turned off while holding a pair): pick the same uuid in single form if it exists, else the first non-empty entry; switch with `forceChange = true`.

Call it from: `AddWeapon`, `RemoveOwnedWeapon`, `Deserialize` (after `ownedWeapons` is read), `Start`, and the `player_character` command.

`IsEntryEmpty()`: melee → false. Otherwise find the owned data (`FindOwnedWeapon(uuid, false)`), or the live `currentWeapon->Data` if that entry is equipped (the live copy is the accurate one, see the note on `ownedWeapons`). Empty = `GetAmmo(type) == 0` and `magazineAmmo <= 0` and (for a pair) `magazineAmmoLeft <= 0`. Treat `magazineAmmo == -1` ("never persisted") as **not** empty when the pool has ammo, empty otherwise.

### Task 4.2: switching

Today switching is lazy: `currentSlot` changes at once, and the update loop (`Player.cpp`, the block starting `if (weaponSystemMode == WeaponSystemMode::Slots && !weaponSuppressed)`) swaps the weapon when `currentWeapon->CanChangeSlot()` allows. Keep that pattern:

- `SelectGridEntry(entry, force)`: if `entry` equals `currentEntry` (uuid and pair), do nothing. Otherwise `lastEntry = currentEntry; currentEntry = entry; weaponGridRevision++;` and if `force` or `CanSwitchSlot`-style check passes, call `SwitchWeapon(...)` now. Do **not** check `weaponSuppressed` here differently from `SwitchToSlot` today: copy its order of checks.
- Replace the lazy block: the weapon needs changing when `currentWeapon == nullptr` or `currentWeapon->Data.inventoryUUID != currentEntry.uuid` or the weapon's pair state differs from `currentEntry.pair`.
- `SwitchWeapon` gets a second parameter `bool pair`. After `Start()`, if the weapon is a `WeaponFirearm`, set a new member `firearm->pairMode = pair` (Task 4.3).
- Keys: `slot1..slot6` → `PressSlotKey(0..5)`. `lastSlot` → `SelectGridEntry(lastEntry)` if `lastEntry` is still in the grid. Add actions `weaponNext` (mouse wheel down) and `weaponPrev` (wheel up) in `GameStart.cpp` next to `slot1..6`. **STOP** if `Input` has no mouse-wheel binding; ask the owner which keys to use instead.
- `PressSlotKey(c)` and `StepWeapon(d)` follow P1 and P2.
- Remove `currentSlot`/`lastSlot`/`weaponSlots` usage from the Slots-mode path. Keep the fields and keep serializing `weaponSlots` and `currentSlot` so old saves still load. In `Deserialize`, if the save has no `currentEntry`, build it from the old `currentSlot`: the single entry of the weapon in `weaponSlots[currentSlot]`.
- Serialize `currentEntry` (uuid, className, pair) and `lastEntry`. Give `WeaponGridEntry` `NLOHMANN_DEFINE_TYPE_INTRUSIVE_WITH_DEFAULT`.
- `RestoreWeapons()` (weapon suppression) uses `SwitchToSlot(slotTarget, true)` today. Change it to re-select `currentEntry` with force.
- `SwitchToMeleeWeapon` and the `slotMelee` action: leave them working. They set `currentEntry` to the melee weapon's entry if it is in the grid, otherwise keep today's code.
- The debug `slotTest` toggle (`firearm->SetAkimbo(!firearm->akimbo)`) is removed; the grid replaces it.

**Check (owner, in game):** pick up pistol and shotgun; keys 2 and 3 switch; pressing 2 twice with `player_character` set to a perk character goes pistol → pistol pair → pistol; save, load, the same entry is held.

### Task 4.3: pair firing and the second magazine

In `WeaponSlotData` (`WeaponBase.h`) add:

```cpp
// Left-hand magazine of a pair (akimbo entry). -1 = never filled. Unused by single entries.
int magazineAmmoLeft = -1;
```
and add it to `NLOHMANN_DEFINE_TYPE_INTRUSIVE_WITH_DEFAULT`.

In `WeaponFirearm`:

- New public `bool pairMode = false;` The effective akimbo state each frame is `pairMode || powerUpAkimbo`. Change `Player::UpdatePowerUps()` so it writes `firearm->akimbo = firearm->pairMode || powerUpManager.IsPowerUpActive(Akimbo)` instead of overwriting `akimbo` with the power-up alone.
- `SetData`: resolve `magazineAmmoLeft` exactly like `magazineAmmo` is resolved today (same two ammo models, same clamping), but only when `akimbo` is true at that moment, or lazily the first time `akimbo` turns on (`SetAkimbo(true)`).
- `PerformAttack`: today `fireLeft = akimbo && alternateFire && fireLeftNext`. Keep that, then: if the chosen hand's magazine is 0 and the other hand's is not, fire the other hand. If both are 0, behave as today for an empty magazine. Take the round from `magazineAmmoLeft` for the left hand and `magazineAmmo` for the right (in the "visual reload" model, both are views of the pool: keep that rule for both).
- `GetRoundsToLoad`/`StartReload`/the reload completion: when `akimbo`, fill `magazineAmmo` first, then `magazineAmmoLeft`, from the same pool, using the existing rules. `CanReload()` is true when either hand would gain a round.
- The power-up pair (D9) uses the same left magazine. When the power-up ends and `pairMode` is false, pour the left magazine back into the pool (`owner->AddAmmo(type, magazineAmmoLeft)`, then `magazineAmmoLeft = 0`) in the clip model only, so ammo is never lost or duplicated.
- `Serialize/Deserialize` of `WeaponFirearm` already write `magazineAmmo` by hand: do the same for `magazineAmmoLeft` and `pairMode`.
- `PlayerState::FromPlayerPtr` already reports `weaponRHandlingType = 2` when `akimbo`: no change.
- `disableOffhandWeapon` already becomes true when `firearm->akimbo`: no change.

**Check (owner):** pistol pair, fire 3 shots → HUD shows `14 · 15`-style counts going down alternately; empty one side → only the other fires; reload fills both; power-up on a single pistol still works and ammo totals stay the same after it ends.

## 5. Icon baking (non-DISTRIBUTION)

Goal: `GameData/textures/ui/weapon_icons/<className>.png`, 512 × 192 (8:3), transparent background, a bone-coloured shaded side view, muzzle pointing **left**, with a 2 px dark outline. The HUD draws it at 150 × 52 with `object-fit: contain`.

### Task 5.1: the baker drawable

New `UI/Player/WeaponIconBaker.h/.cpp`, the whole file inside `#ifndef DISTRIBUTION`.

Model it on `UiBilboard::PreDraw()` / `DrawUi()` (`Engine/UI/WorldSpace/UiBilboard.cpp`): a drawable whose `PreDraw()` runs inside `Renderer::RenderLevel` (after `FinalizeFrameData`, before the camera passes) and renders into its own target.

```cpp
class WeaponIconBaker : public Entity   // spawned once by Player::Start in non-DISTRIBUTION builds
{
    // queue of WeaponDef to bake, the one in progress, its mesh, the targets
};
```

Per weapon, one at a time:

1. **Decide whether to bake.** Bake when the source icon is missing, or the model file is newer than the icon (`std::filesystem::last_write_time` on both source paths, §5.3), or the console command `weapon_icons_rebake [className]` asked for it.
2. **Load the mesh** as a `StaticMesh` (owned by the baker, not visible in the level: `Visible = false` for the normal camera, or not added to the level's render list; read how `UiBilboard`/`StaticMesh` register so it is not drawn in the world). Use `LoadAssetsIfNeeded()` and wait frames until the model is loaded (`AssetLoadState`).
3. **Fit the camera.** Rotate the mesh by `iconRotation`. Take its model-space `GetBoundingBox()`. Orthographic projection (`glm::ortho`) looking along the axis that shows the weapon's side, sized to the box with 6 % margin, keeping the 8:3 aspect. Find the side axis by testing one weapon (pistol) and writing it down in a comment; per-weapon fixes go in `iconRotation`, not in code.
4. **Render target.** `RenderTexture` colour RGBA8 512 × 192 + `RenderTexture` depth `Depth24`, both attached to a `Framebuffer` (see the usage comment at the top of `Renderer/Abstractions/FrameBuffer.h`). Create them once, reuse them for every weapon.
5. **Draw like the renderer.** In `PreDraw()`:
   - draw commands submit to `ViewIdManager::GetCurrentId()` (`StaticMeshDrawCommand::DrawForward` → `SubmitIndexed(..., GetCurrentId())`). So do what `Renderer::RenderCameraForward` does: `framebuffer.bind(0, 0, 512, 192)` makes a fresh current view for the target (read `Framebuffer::bind` to confirm it calls `ViewIdManager::GiveNextId()`; `UiBilboard::DrawUi` relies on the same thing through `setAsRenderTarget()`). Never cache the view id across frames;
   - `setViewMode(Sequential)`, clear colour `0x00000000` and depth 1 on that current id;
   - collect the mesh's draw commands with `CollectDrawCommands(outCommands)` (the same call the level uses);
   - on each `StaticMeshDrawCommand`, set fixed lighting for the icon: `LightAmbientColor = vec3(0.35)`, `LightDirectColor = vec3(1.0)`, `LightDirection = normalize(vec3(-0.4, -1, -0.6))` in view space terms (adjust once by eye), `IsViewmodel = false`;
   - set the depth state the forward pass uses (`BgfxStateManager` calls in `Renderer::RenderCameraForward`) and call `cmd->DrawForward(iconView, iconProjection)`.
   - the forward shader reads lighting uniforms through `Renderer::SetSurfaceShaderUniforms` (sun direction, shadow maps). Directional shadows may darken parts of the icon: if they do, render while `LightManager::DirectionalShadowsEnabled` is temporarily false and restore it right after the draw calls. **STOP** if the icon still comes out black or unlit; report what the shader reads.
6. **Read back.** One frame after drawing, call `Screenshot::RequestTarget(colorTexture, 512, 192, tempPath)` with `tempPath = "SaveData/weapon_icons_raw/<className>.png"`. The file appears a few frames later. Wait until it exists and its size stops changing before Task 5.2.

### Task 5.2: finishing the image (CPU)

Load the raw PNG with `stbi_load` (already in the engine; grep for its include). Then, per pixel:

1. `a = alpha`. Pixels with `a < 8` become fully transparent.
2. Grey value `g = luminance(rgb)`; remap to the bone palette: `out = mix(#4a4038, #e6dcc4, smoothstep(0.05, 0.85, g))`. This keeps the model's shading but makes every icon the same family of colours.
3. Outline: any transparent pixel within 2 px of an opaque pixel becomes `#000000` at alpha 200.
4. Crop to the opaque bounds + 4 px, then letterbox back to 8:3 centred, and scale to 512 × 192 (`stbir` if the engine has it, otherwise keep the crop and pad).
5. Write with `stbi_write_png` to the **source** icon path (§5.3) and copy the same bytes to the running `GameData/textures/ui/weapon_icons/` so this session sees it without a rebuild.

The HUD tints with CSS filters (§6), so the PNG stays in bone colours.

The engine already knows that folder for `UiSourceSync.cpp` through the CMake define `ENGINE_GAME_SOURCE_DATA` (root `CMakeLists.txt`, the `set_source_files_properties` line for `UiSourceSync.cpp`).

- Add one line next to it so `WeaponIconBaker.cpp` gets the same define:
  `set_source_files_properties("${GAME_DIR}/UI/Player/WeaponIconBaker.cpp" PROPERTIES COMPILE_DEFINITIONS "ENGINE_GAME_SOURCE_DATA=\"${GAME_DIR}/GameData\"")`
  It only applies when that file exists, so the other games are unaffected.
- If the define is empty (some other build path), log one warning and write only to the running copy.
- **STOP** if the StealthAction build the owner uses is the `.vcxproj` and not CMake. Ask how to pass the path.

**Check (owner):** delete one icon from source `GameData`, start the game, the icon reappears in source `GameData` within a few seconds, opens in an image viewer as a bone-coloured side view with the muzzle on the left. ## Implementation notes

**Status (2026-11-12): implemented in one pass; not yet checked in game.**

Owner decisions after the plan was written:

- Hand cannon: no akimbo (`None`). No weapon is `Only` yet.
- Pistol is `Always` **for testing** (nobody knows yet which weapon is always paired). Silenced pistol and revolver are `WithPerk`.
- Every playable character has its own health figure: `hudSilhouette` column in `GameData/tables/characters/characters.csv`. The HUD draws that one image twice, tinted with `wash-color` (bone for the body, dried blood for the damage), so a figure is a single white SVG/PNG.
- A test character `duelist` (AkimboPerk on) exists so the perk can be tried: console `player.character duelist`.

Differences from the plan above:

- **P3 dropped.** The existing akimbo ammo model is kept: the right gun owns the magazine, the left gun fires straight from the ammo pool (see `WeaponFirearm::PerformAttack`). There is no `magazineAmmoLeft`; the HUD shows `magazine / reserve` for pairs too.
- `WeaponFirearm::pairMode` is set by `Player::SwitchWeapon(data, pair)`; it sets `akimbo` directly. `Player::UpdatePowerUps()` (not called anywhere today) now keeps a pair a pair.
- The debug `slotTest` (T) akimbo toggle is removed.
- Weapon switching: number keys and mouse wheel (`Input::MouseScrollDelta`); no new input actions.
- The icon baker (`UI/Player/WeaponIconBaker.cpp`) is an `IDrawMesh` whose `PreDraw` binds its own `Framebuffer` (fresh view id) and calls the weapon mesh's `DrawForward` with an orthographic side camera; the capture goes through `Screenshot::RequestTarget`, then CPU recolour + outline. Camera looks along -X; fix a weapon's facing with `iconYaw/Pitch/Roll` in the table. Console: `weapon_icons.rebake [class]`.
- HUD: `UI/Player/PlayerHudView.*` + `GameData/ui/hud/player_hud.xml/.css`. It is inserted into the viewport below the menu stack and fades while a page with `hides-hud` is open. Old `WeaponSlots`, `UseIndicator`, `StaminaBar`, `HudStatusBar`, `HudStatElement` are gone.
